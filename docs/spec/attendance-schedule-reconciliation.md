# 排班與出勤核對

## 操作方式

側邊欄使用「排班與出勤」，舊 /attendance、/schedule 連結仍可使用。出勤與班表檢視各自遵守原權限，查詢日期沿網址 date 參數保留。

1. 在出勤頁選月份並匯入打卡。匯入完成會切到「班表與打卡核對」。
2. 選擇最多 31 天的核對起迄日。系統以在職人日及班表比對，不只檢查檔案中出現的人。
3. 尚未確認完整匯入時，無卡者列「資料待補」。只有確認涵蓋該期間全部員工及所有打卡來源後，勾選完整性並重新核對，才將應出勤且無卡者列「疑似缺勤」。今天及未來不能確認為完整日期。
4. 檢視原班表、原始打卡、候選班別及理由。候選以兩張卡各距離班別起訖 15 分鐘內為篩選，這是建議範圍，不是遲到寬限，不自動更新班表。
5. 管理員確認實際班別或當日排休並填原因。只有唯一符合互換條件的同日對象會提供一併確認選項，必須明確勾選；兩人以同一交易處理。
6. 缺卡／異常可直接前往所點日期月份的員工明細補卡；完全無紀錄時，可從該列開啟「補匯入當日紀錄」。疑似缺勤仍須核查漏卡、請假或跨日調休。

## 保護與限制

- 完整性聲明只適用本次查詢，換日期／重新匯入會清除，不是系統對檔案完整性的保證。
- 不自動把推測當事實，不修改原始打卡，不因核對清單的疑似缺勤標籤直接做薪資裁定。
- 確認時重新檢查班表、打卡、請假等版本；409 表示需重新核對，不能沿用舊建議重送。
- 已有出勤的歷史班表異動由核對入口確認重算，舊每日／週排班匯入等入口會明確拒絕相關異動。
- 確認需要出勤寫入及排班權限；封存、自我裁定及租戶隔離守衛仍適用。
- 特休抵銷、多筆部分假、跨夜部分假及共用薪資邏輯無法安全處理的全日覆蓋組合，需個別核查；新入口會說明原因並拒絕不安全的確認。
- 第一版只建議同日換班；跨日期調休不自動配對。

## 技術與驗證

新契約：POST /attendance/reconciliation/preview、POST /attendance/reconciliation/confirm-shift；型別由本次後端 OpenAPI 產生。無新資料表、無 migration；沿用 DailyShift、Attendance、AuditLog 及薪資待重算機制。

前端主要驗證：useAttendanceReconciliation、ReconciliationPanel、AttendanceScheduleHubView、AttendanceWorkspaceView、ScheduleView 與 navigation parity。後端包含租戶 A/B、無 context、封存、自我、版本更新、兩人交易回滾、缺列、請假及既有歷史班表入口防護。隔離 PostgreSQL 真正並行交錯與線上操作需另行驗證，不能用 SQLite 或查詢編譯斷言替代。
